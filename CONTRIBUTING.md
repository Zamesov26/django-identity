# Участие в разработке

## Коммиты

Проект использует Conventional Commits. Сообщение коммита должно иметь формат:

```text
<type>(<scope>): <description>
```

`scope` необязателен. Описание пишется на английском языке, в повелительном
наклонении, со строчной буквы, без точки в конце. Рекомендуемая длина первой
строки — не более 72 символов. Один коммит должен содержать одно логическое
изменение.

Допустимые типы:

| Тип | Назначение | Изменение версии |
| --- | --- | --- |
| `feat` | Новая обратно совместимая функциональность | `MINOR` |
| `fix` | Исправление ошибки | `PATCH` |
| `perf` | Обратно совместимое улучшение производительности | `PATCH` |
| `build` | Сборка и зависимости | нет |
| `ci` | CI/CD | нет |
| `chore` | Служебные изменения | нет |
| `docs` | Документация | нет |
| `refactor` | Рефакторинг без изменения поведения | нет |
| `style` | Форматирование без изменения поведения | нет |
| `test` | Тесты | нет |

Примеры:

```text
feat(tokens): propagate delegated actor chain
fix(drf): reject expired access tokens
docs: explain service identity settings
test(identity): cover system actor without subject
```

Тип `revert` не используется: conventional parser `python-semantic-release` не
обрабатывает его как отдельную категорию релиза. Если откат исправляет поведение,
используйте `fix`, например `fix(tokens): revert audience validation change`.

### Несовместимые изменения

Несовместимое изменение помечается `!` после type или scope и обязательно
содержит footer `BREAKING CHANGE:` с описанием миграции:

```text
feat(identity)!: replace issuer setting with service name

BREAKING CHANGE: replace IDENTITY.JWT.ISSUER with IDENTITY.SERVICE_NAME.
```

Пока версия проекта меньше `1.0.0`, такое изменение увеличивает `MINOR`:
`0.1.0 → 0.2.0`. После выпуска `1.0.0` оно будет увеличивать `MAJOR`.

### Pull requests и релизы

При squash merge заголовок pull request становится сообщением коммита, поэтому
он должен соответствовать этим же правилам.

Релиз запускается вручную workflow `Release` только из ветки `main`.
`python-semantic-release` анализирует все коммиты после последнего тега и
выбирает наибольшее требуемое изменение версии: `feat` сильнее `fix`, а breaking
change сильнее обоих. Несколько коммитов одного типа не увеличивают версию
несколько раз.

Версию в `pyproject.toml`, релизные секции `CHANGELOG.md` и Git-теги вручную не
изменяем — это делает release workflow. Сгенерированный релизный коммит имеет
вид `chore(release): X.Y.Z`.

До первого запуска workflow владелец репозитория один раз создаёт исходный тег
на коммите с версией `0.1.0`:

```shell
git tag -a v0.1.0 -m "Release 0.1.0"
git push origin v0.1.0
```

Без исходного тега в расчёт первой автоматической версии могут попасть старые
коммиты, созданные до введения этих правил.
